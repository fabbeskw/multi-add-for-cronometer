# Store assets: the Chrome Web Store screenshots

Five 1280 x 800 PNG screenshots (24-bit RGB, no alpha, as the Developer Dashboard requires) of the **real
extension over the real Cronometer diary**, produced by `tools/screenshots.py`, plus `manifest.json`, which
records for each file what it shows, when it was captured and what was blurred. Regenerate them after any
visible change to the panel (see *Regenerating*); the dashboard accepts up to five, in this order.

**The PNGs are not committed.** `.gitignore` excludes `store-assets/*.png` (and `dry-run/`) because a live run
captures a real account's diary. The live PNGs that may sit in a working copy were captured on 2026-09-28 (see
`manifest.json`) on Chrome 150 with extension version **0.2.0** and show a real diary; they are not the release
set. Before the next store upload, and after any visible UI change (0.2.1 or later), **regenerate them** with a live
run, and have **the account owner review every PNG** (see *Before uploading*) before anything is uploaded or
force-added to git. `dry-run/` is the output of the tool's self-check against the mock diary
(`tests/mock-cronometer.html`); it is regenerated by the test green bar and is **not** store material.
Version 0.3.0 adds the **TDEE** tab, which neither the five shots nor `tools/screenshots.py` cover yet; it shows weight
and intake, so a shot of it needs the account owner's explicit agreement (see STORE-LISTING.md, screenshot checklist).

## How they were made

`tools/screenshots.py` (Python 3 stdlib, no PIL) drives Chrome through the DevTools Protocol over
`--remote-debugging-pipe` (`tools/cdp.py`, the client `tools/smoke_extension.py` uses as well):

1. starts a **visible** Chrome on a temporary profile, sizes the window so the page viewport is 1280 x 800 and pins
   the viewport with `Emulation.setDeviceMetricsOverride` (1280 x 800, device scale factor 1), so every capture is
   exactly 1280 x 800 whatever the window;
2. installs the extension from the repository with `Extensions.loadUnpacked` (Google Chrome 137+ ignores
   `--load-extension`) **before** the diary is opened, so the extension sees the app start; opens
   `https://cronometer.com/#diary`;
3. waits for **you** to log in (up to 15 minutes; it never touches the login form; it only sets `#diary` when the app
   lands on another view), until the page has the app iframe, the diary FOOD button and the extension's panel host,
   then until the extension has captured the session from the app's own start-up traffic;
4. drives the extension through its **own isolated world** (`Runtime.evaluate` in the execution context whose origin
   is `chrome-extension://<id>`): mounts the panel, saves the engine setting, types the list into the real textarea,
   picks Dinner, presses the real **Find foods**, **Add all** (RPC engine: real `updateDiary` requests) and later
   **Undo this batch** buttons, and waits for each view to settle (bounded waits with clear messages);
5. before every capture injects the blur CSS into the page's MAIN world (`filter: blur(9px)`): the built-in selector
   list (authored class names found in Cronometer's compiled client: the Pro navbar account switcher
   `#navbarDropdown` / `.navbar-account` / `.navbar-dropdown-container`, the page header `#cronometer-header`, the
   diary's `.energy-summary*`, `.target-summary-container`, `.nutrient-targets-container`, `.macro-targets` and
   water-target bars), every element whose text carries the account's first name or e-mail address (read from the
   app's own User object in the page, never printed or stored) and, in the Diagnostics dump, the numeric account id;
6. captures with `Page.captureScreenshot` (PNG, the viewport clip, `captureBeyondViewport: false`), writes the five
   files and `manifest.json`, presses **Undo this batch** and waits for the panel's outcome line ("Undo: 4 removed,
   0 failed"), then verifies every PNG (IHDR 1280 x 800, no alpha, decoded rows not blank) and prints `SCREENSHOTS PASS`.

The undo is armed the moment **Add all** is pressed, so it runs even when a later step fails, times out or is
interrupted with Ctrl+C (a `finally` block): it first waits (up to 60 s) for a batch that is still running, then
presses **Undo this batch**; if the Results view never rendered it falls back to the Input view's **Undo last
batch**, then to the panel's own undo of `CMA.engineRpc.lastBatch`. After Ctrl+C exactly one bounded undo attempt is
made (a second Ctrl+C skips it). Whenever the undo did not start or its outcome is unknown, the script ends with
`WARNING: entries were added and NOT undone - remove them by hand`: then remove the four entries in the diary
yourself. Nothing is typed into any login form, no cookie is read, the session token never leaves the extension.
Before Chrome closes, the temporary profile's cronometer.com storage and all its cookies are cleared, and the
profile folder is then deleted (retried for 10 s; a folder that cannot be deleted is printed prominently, delete it
by hand).

**`--profile DIR` keeps a logged-in Cronometer session on disk**: that folder is neither cleared nor deleted, so a
second run needs no login, and anyone who can read it can use your account. Keep it private and delete it when you
are done.

## Regenerating

```
python tools/screenshots.py                  # live: opens a Chrome window, waits for your login, writes store-assets/*.png
python tools/screenshots.py --dry-run        # the same flow against tests/mock-cronometer.html (UI engine), writes store-assets/dry-run/
python tools/screenshots.py --dry-run --headless   # the self-check the test green bar runs (no window)
```

Options (`--help` prints them with this tool's full description): `--out DIR` (default `store-assets/`),
`--profile DIR` (use and keep a Chrome profile, logged in: a second run then needs no login; see above), `--keep-open` (leave the window until Enter is pressed), `--chrome PATH`, `--login-timeout MIN`,
`--engine rpc|ui` (only the RPC engine has an undo; with `ui` the four entries stay in the diary), `--delay-ms N`,
`--lines FILE` (your own input lines: add a line whose unit the food does not have, e.g. `2 slices banana`, to get a
`?` row with a *Use ...* suggestion in the preview, as STORE-LISTING.md's checklist suggests), `--blur-selectors "a, b"`
(more CSS selectors to blur), `--blur-text TEXT` (blur every element containing that text; repeatable), `--no-blur`
(nothing blurred: never for shots you upload). Exit status: 0 PASS, 1 FAIL (a step, a capture or the verification),
2 environment (Chrome, DevTools pipe, extension install), 3 login not completed in time / interrupted.

What you do during a live run: log in in the window that opened (any way you like; the script only watches the DOM),
then leave the window alone. The console reports each step; the whole scenario takes about 20 seconds after the login.
The run adds four real entries to the diary day shown and removes them again at the end; the console prints the undo
outcome and whether the diary still shows any of them.

### What the dry run covers, and what it does not

`--dry-run` runs the same code against the mock diary: the extension scripts in an isolated world named after the
extension (found by name, as in the live run), the real panel buttons, the UI engine, the captures, the MAIN-world
blur CSS, the text blur (a synthetic name / e-mail label and a text input on the mock page are marked; a password
input and an `autocomplete=current-password` field are not) and the Diagnostics account-id blur (a synthetic id);
the tool fails unless the dry-run `manifest.json` lists those blur entries. It does **not** cover: the undo (the
RPC engine and its Undo buttons), the real login wait and the `#diary` nudge, the session capture
(`CMA.capture.ready`), reading the name / e-mail from the app's User object, the default blur selectors against the
real Cronometer layout, and the session clearing against a real login. Those only run live.

## Before uploading

* The account owner reviews every PNG before it is uploaded (or force-added to git): the shots show a real diary.
* Open every PNG and look for anything personal the blur did not cover (a widget Cronometer added since, a name in a
  place the tool does not know): pass `--blur-selectors` / `--blur-text` and run again rather than editing the PNGs.
* The diary entries visible in the shots are yours by design (the tool never blurs them): capture on a day whose
  entries you are happy to show, or on an empty day.
* `manifest.json` lists what was blurred per shot; keep it next to the PNGs (it is not uploaded).
* Upload in file order (01 to 05); the dashboard takes 1280 x 800 PNG/JPEG without alpha. No cropping is needed: the
  browser UI is not part of a capture.
