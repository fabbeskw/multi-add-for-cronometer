# Multi-Add for Cronometer — implementation spec (v1)

Chrome extension (Manifest V3) that lets a logged-in Cronometer **web** user add many foods to the diary in one go.
Cronometer's web "Add Food to Diary" dialog closes after every add and has no multi-add (mobile only, verified 2026-09-27).

Everything below is grounded in the research under
`<session scratchpad>` (a local, untracked research folder from the session that wrote v1:
`research/*.md`, `live/all.js` = the live compiled GWT bundle, `repos/*` = unofficial clients; not part of the
repository — `tools/fetch_bundle.py` recreates the bundle under `tools/bundle/`). Cite those files when unsure.
We could NOT log in, so nothing has been tested against a live account. The design therefore ships **two engines**
(RPC and UI-automation), a **diagnostics panel**, and an **undo**, so the user can fall back and report.
Status (2026-09-28): live-tested — 3 foods were added through the RPC engine and undone, and the UI-automation
engine worked as well (the paragraph above records the situation when v1 was written). Extension name since 0.2.0:
**Multi-Add for Cronometer** (was *Cronometer Multi-Add*; the `CMA` namespace, the `cma-` CSS prefixes and the
`cma*` storage keys are unchanged; see §11 and Appendix D). Since 0.3.0 the extension also carries an optional
**Adaptive TDEE** tab (§12, Appendix I): an expenditure estimate and weekly check-in computed from the intake and
weight already logged in Cronometer, read through the web app's own read RPCs only after the user enables it. Its
data layer has NOT been exercised against a live account yet (§12.6).

## 0. Non-negotiables

* Plain JavaScript (ES2020), NO bundler, NO npm, NO TypeScript. Content scripts are classic scripts sharing one
  namespace: every lib file starts with `window.CMA = window.CMA || {};` and attaches to `CMA.*`. Load order is set in
  `manifest.json` and mirrored in the test pages.
* All network traffic is same-origin to `https://cronometer.com` from the ISOLATED-world content script (cookies are
  sent automatically). Never contact any other host. Never read `document.cookie`. Never persist the session token
  (`nonce`) to `chrome.storage`; keep it in memory only, and redact it in every log/diagnostic string.
* Never call the `authenticate` RPC ourselves (it rotates the session nonce and would break the running app).
* No `eval`, no inline scripts in extension pages (MV3 CSP). Panel UI lives in a Shadow DOM under `:host{all:initial}`.
* Every RPC we send mirrors what the real UI sends (see §4). One `updateDiary` per food (SingletonList), sequential,
  with a delay (default 250 ms). Do not batch N changes in one call (server behaviour untested).
* Tests run in headless Chrome: `"C:/Program Files/Google/Chrome/Application/chrome.exe" --headless=new --disable-gpu
  --no-sandbox --virtual-time-budget=20000 --dump-dom file:///<abs>/tests/<page>.html`. A test page writes results into
  `<pre id="results">` and the literal line `ALL TESTS PASSED` when green, `FAILED: n` otherwise. `tests/run.sh` runs
  every page and exits non-zero on failure; it judges ONLY the `#results` block (a whole line equal to the verdict),
  never the dumped page source — a page whose script mentions the literal (registry-builder.html's `?realtime=1`
  branch) would otherwise pass whatever its results say (review round 4 found exactly that). There is no node.

## 2. Session capture (hook-main.js + capture.js)

### 2.1 Facts
* The GWT app runs in a hidden same-origin `<iframe id="cronometer">` but does `var $wnd = window.parent` and creates
  requests with `new $wnd.XMLHttpRequest`, so patching `XMLHttpRequest.prototype` on the TOP window in the MAIN world at
  `document_start` captures every RPC and every `/api/v3/` XHR. All widgets live in the TOP document.
* GWT-RPC: `POST https://cronometer.com/cronometer/app`, headers `Content-Type: text/x-gwt-rpc; charset=utf-8`,
  `X-GWT-Permutation: <32 hex>`, `X-GWT-Module-Base: https://cronometer.com/cronometer/`. A second service `/cronometer/pro`
  exists (ignore). Responses start with `//OK` or `//EX` (HTTP 200 in both cases).
* The first `java.lang.String` parameter of every user RPC is the session nonce (`$c.Q` on the User object; the same
  value the `sesnonce` cookie carries). It is set by `authenticate` at page load and only rotates on
  `authenticate`/`reauthenticate`. We take "the nonce the app used most recently" as truth.
* Permutation and policy hash change on every Cronometer deploy (4 permutations in 7 months). Read them from traffic:
  permutation = `X-GWT-Permutation` header; policy hash = 2nd string of any request body; module base = 1st string.
  Fallback for permutation: `document.querySelector('script[src*=".cache.js"]').src` matches `/([0-9A-F]{32})\.cache\.js$/`.
* `authenticate(Integer utcOffsetMinutes)` is the first RPC after load; its `//OK` payload is a
  `com.cronometer.shared.user.models.User/91151502` object: field index 19 = userId (int), index 33 = session key (string),
  and somewhere in the graph a `java.util.HashMap` whose keys include `DG01`..`DG08` (group names) and `DG01ON`..`DG08ON`
  (`'true'`/`'false'`) and `DG_ON`. Do not depend on the map's field index: search the deserialized graph for a Map that
  carries any `DG0n` / `DG0nON` / `DG_ON` key; `decodeGroups` then returns all 8 groups exactly like the app's own
  dropdown builder `cNh` (`for(c=1;c<9;c++){alo('true',WBk(a,'DG0'+c+'ON',''+(c<6)))&&Yze(b,''+(c-1),WBk(a,'DG0'+c,J_i[c-1]))}`):
  a missing name means the default name, a missing ON flag means enabled for ids 0..4 and disabled for 5..7.
  (In build 0A1C16E1… that map is the `HashMap` subclass
  `com.cronometer.shared.user.models.UserPreferences` at User field index 28; the registry marks such subclasses
  `{k:'map', sub:true}` and they decode to a plain `Map`. Key `DG0<n>` / `DG0<n>ON` belongs to group id `n-1`:
  the diary code `Lrd` reads `DG0<f>ON` for f = 2..8 as group f-1, so `DG02` is Breakfast = id 1.)
* `getDayInfo(String nonce, Day day, int userId)` fires whenever the diary shows a day; its Day param is the diary date
  currently viewed. `getDayInfo` returns `DayInfo/416556043` = [bool, Day, ArrayList, ArrayList, bool, String]; lists c
  and d contain the day's entries (Servings among other entry types).
* userId also appears in every `/api/v3/user/{id}/...` URL.

### 2.2 hook-main.js (MAIN world, no chrome.* APIs)
Patch `open`, `setRequestHeader`, `send` on `XMLHttpRequest.prototype`. For requests whose URL matches
`/\/cronometer\/(app|pro)(\?|$)/` or `/\/api\/v3\//`, on `loadend` post ONE message to the content script
(review round 2: over the MessageChannel port the content script's ping hands over — see "Transport" below —
never live on `window` before that ping):
```
{ source: 'cma-hook', type: 'xhr', method, url, requestHeaders: {...}, requestBody: string|null,
  status, responseText: string|null, responseHeaders: string, t: Date.now() }
```
Also poll (every 250 ms, up to 60 s) for `document.getElementById('cronometer')?.contentWindow?.$strongName` and post
`{ source:'cma-hook', type:'gwt', strongName, moduleBase }` once. Never throw into the page; wrap everything in try/catch.
Also listen for `{source:'cma-content', type:'ping'}` and answer `{source:'cma-hook', type:'pong', hooked:true}` so the
content script can tell whether the hook is installed (extension loaded after page load ⇒ no hook ⇒ ask user to reload).
Early-traffic buffer (implemented; tests/hook.html): the content script is injected at `document_idle`, which can be
after the app's first RPCs have completed, and `authenticate` is the only source of the diary groups. So every `xhr`
message carries a per-page `seq` (1, 2, …) and is also kept in a bounded buffer (100 messages / 4 MB of bodies)
until the first ping; the ping handler replays the buffer in wire order with `replay:true`, then posts
`{type:'pong', hooked:true, replayed:n, seq}`, and buffering stops for good. content.js handles each `seq` once (a
message that was both delivered live and replayed is processed a single time), so "ONE message per request" holds
for the capture.
Origin, size and eviction rules (review round 1): only URLs on the page's own origin are relayed — the bundle
initialises Braze/Amplitude in the TOP window and their SDK traffic uses `/api/v3/` paths on other hosts (on an
opaque `file:` test page relative/`file:` URLs pass and any http(s) host is foreign). `/api/v3/` messages carry
`requestBody: null, responseText: null` (capture reads only url/status/method/headers of REST traffic); RPC
responses are relayed in full only for `authenticate`, `updateDiary`, `getDayInfo` and `getFood` (the methods
capture decodes) and cut to their first 4096 chars otherwise (enough for `//OK`, `//EX` and an exception
payload). When the pre-ping buffer overflows, the oldest message that is NOT the `authenticate` exchange is
evicted (`tests/hook-buffer.html`).
Transport (review round 2): a `message` event on `window` reaches every listener of every world, and the bundle
runs Braze/Amplitude in the TOP window, so the relay never puts the nonce or a response body on the window.
content.js sends each ping as `window.postMessage({source:'cma-content', type:'ping'}, origin, [port2])` with a
fresh `MessageChannel` (a port transfers once, so every retry carries a new one) and listens on `port1`; the
hook adopts the port of the ping it answers (latest wins) and sends the replay, the pong, the `gwt` message and
every later `xhr` message with `port.postMessage`. Before the first ping xhr messages are ONLY buffered (nobody
legitimate listens yet; the `gwt` info is stored and sent with the pong). A port-less ping (older test pages)
is answered on the window, and the window stays the fallback when no port was ever adopted or the port throws.
content.js still accepts window messages (same source + origin checks) and de-duplicates xhr messages by `seq`
on both paths. Only the ping/pong itself is ever visible to page scripts and it carries no data.

### 2.3 capture.js (ISOLATED)
`CMA.capture` keeps `state`:
```
{ hooked:bool, moduleBase, permutation, policyHash, nonce, nonceUpdatedAt, userId,
  groups: [{id:0..7, name, enabled}], groupsSource:'authenticate'|'dom'|'default',
  diaryDate: {day,month,year}|null, diaryDateSource:'getDayInfo'|'today',
  lastRpcAt, rpcCount, lastError, throttleVersion, log:[...(max 200, redacted)] }
```
`CMA.capture.handleMessage(data)`:
* `type:'gwt'` → permutation/moduleBase if missing.
* `type:'xhr'` with a GWT body → `CMA.gwt.parseRequest(body)` (§3.4) → set moduleBase/policyHash/method; if param 0 is
  `java.lang.String/2004016611` its value is the nonce (update `nonce` whenever it differs); extract userId when the
  params before it are only strings/primitives/Day/Time (e.g. `updateDiary(String,int,List)` → 2nd param;
  `getDayInfo(String,Day,int)` → 3rd). For `getDayInfo` also set `diaryDate` from the Day param. Read
  `X-GWT-Permutation` from requestHeaders. If `responseText` starts with `//OK` and method is `authenticate`, decode
  with `CMA.gwt.readResponse` and pull userId (field 19), session key (field 33 → nonce if none yet) and the DG map
  (→ groups). If method is `reauthenticate` (the app calls it with the OLD key whenever one of its RPCs answers
  NotLoggedInException and stores the STRING result as the new key: `P1b` → `pYb` → `iDk($c, a)`), decode the
  `//OK` with kind `'s'` and set the nonce to it (source `'reauthenticate'`); the request side of that method is
  never adopted as the nonce (it is the rejected key by construction). Track `X-Cronometer-Throttle-Version`
  from responseHeaders. If `responseText` starts with `//EX` and contains `NotLoggedInException`, set
  `lastError = 'session'`.
* `type:'xhr'` with url `/api/v3/user/(\d+)/` → userId (same-origin URLs only: `userIdFromUrl` is null for another host).
* Every `xhr` message from another origin is dropped before any of the above (`state.ignoredForeign++`), and a
  `moduleBase` on another origin (request body, `gwt` message or `<script>` probe) is never adopted (SPEC §0;
  rpc.js additionally refuses a moduleBase whose origin differs from `location.origin` on https pages).
* `//OK` responses of `updateDiary`, `getDayInfo` and `getFood` are decoded: a decode failure is logged as kind
  `decode` naming the offending type signature (stale registry), a `parsed.paramError` as a `warn`, and an
  `ErrorEntryChangeResult` inside an `updateDiary` result list puts `rejected:true, rejectMessage` on the `'rpc'`
  event (the panel's UI-engine refresh signal then fails that row). `state.registryMismatch` is true while the live
  permutation differs from `CMA.registry.permutation` (Input-view banner "Cronometer deployed a new build").
* `'rest'` events and log entries carry the URL **pathname only** (the food-search query string is the food name).
* Emits `CMA.events.emit('state', state)` after each change (simple pub/sub in `CMA.events`).
Group fallbacks: if no authenticate seen, read `.diary-group-title` texts from the DOM (ids unknown ⇒ assume the
displayed groups are the enabled ones in id order starting at the first enabled default id, low confidence, mark
`groupsSource:'dom'`); else defaults `['Uncategorized','Breakfast','Lunch','Dinner','Snacks','Group 6','Group 7','Group 8']`
with ids 0..7, enabled 0..4.
`CMA.capture.ready()` → `{ok, missing:[...]}` requires hooked, nonce, userId, permutation, policyHash, moduleBase.
Also: `CMA.capture.session()` → the `{moduleBase, permutation, policyHash, nonce, userId}` object rpc.js takes;
`snapshot()` (JSON-safe copy, nonce redacted), `probeDom(doc)`, `waitFor(pred, {timeout, label})` → Promise of the
next 'rpc'/'rest' event `pred` accepts, `log(kind, fields)` (redacted ring buffer, never bodies), `redact(str)`.
Events: `'state'` (after every change), `'rpc'` ({service, method, status, ok, ex, date, t, parsed}), `'rest'`
({method, path, status, t}). userId sources are ranked (authenticate > v3-url = known method > generic first-int) so
a low-confidence guess never overrides a better value; the policy hash is inferred from the registry while the
permutation equals the analysed bundle's and no request body has been seen yet.
Since 0.3.0 (§12.2): `USER_ID_PARAM` also knows getCaloriesConsumedAndBurned, getCalendarInfo, getBiometrics and
setUserPreference (userId = param 1), and the `'rpc'` event of a `setUserPreference(String, int, String key, String
value)` carries `pref: {key, value}` for the TDEE data layer; the log line names the key (`prefKey`), never the value.

## 3. GWT-RPC stream (gwt-stream.js + registry)

### 3.1 Wire format
Request body = tokens joined by `|` with a trailing `|`:
`7|0|<nStrings>|<string 1>|...|<string n>|<moduleBase idx>|<policy idx>|<service idx>|<method idx>|<nParams>|<param type idx>...|<values...>|`
Indices are 1-based into the string table; `0` = null string/object. Strings are interned in first-use order (the
module base, policy hash, interface name, method name, param type sigs first, then values as encountered). Escaping
(client `C1n`): `\` → `\\`, `|` → `\!`, `\u0000` → `\0`, and chars matching the browser regex (for Chrome:
`/[\u0000\|\\\uD800-\uFFFF]/g`) → `\uXXXX` (4 hex, lowercase). Booleans: `1`/`0`. Ints/bytes/shorts: decimal.
(Escape-regex note: `B1n` picks the regex from the user agent; desktop Chrome's UA contains "webkit", so the real
client uses the long webkit character class — `CMA.gwt.ESCAPE_RE_WEBKIT`, the default, which also escapes
combining-mark ranges — while the class quoted above is `B1n`'s fallback for unknown browsers,
`CMA.gwt.ESCAPE_RE_DEFAULT`; `escapeString(s, re)` takes either. The server accepts both and they agree on every
character of the RPC templates.)
Doubles: JS `''+x` (so `50` not `50.0`; the server accepts both). Longs: GWT base64 (`T0n`/`Q0n`): split the 64-bit value
into hi/lo 32-bit ints, emit 6-bit groups MSB-first using alphabet `A-Z a-z 0-9 $ _`, **skipping leading zero groups**;
value 0 → `A`. Objects: `writeObject(obj)`: null → `0`; already written (identity) → `-(k+1)` where k is its 0-based
index among written objects; else intern its type signature string, emit that index, register the object, then
write its fields per the serializer. Collections: `java.util.ArrayList/4159755760` = size int then elements
(each via writeObject); `java.util.Collections$SingletonList/1586180994` = the single element only (NO size).
Response = `//OK` + a JSON array. Layout: `[ ...payload tokens..., [string table], flags, version ]`. The client reads
the array **from the end**: version, flags, string table, then payload tokens backwards. So payload token i in write
order sits at `arr[len-4-i]`. Strings in the payload are 1-based indices into the table (0 = null). Object = readInt
type index (0 → null; negative → back-reference to the (−n−1)-th previously *instantiated* object; positive → the
type signature `table[idx-1]`), then instantiate + read fields. Longs arrive as base64 strings (or plain numbers;
accept both). Booleans arrive as `1`/`0` (or true/false; use `!!`). `//EX[...]` has the same layout; its payload
is a Throwable subclass whose deserializer reads one string (detail message) and possibly an object (cause) first.
Parse the JSON with `JSON.parse(text.slice(4))`; if that throws (version < 8 uses JS literals with single quotes),
fall back to `Function('return ' + text.slice(4))()` **only in tests**, never in the extension (CSP) — in the
extension, convert `'`-quoted strings to JSON by a careful tokenizer or treat as failure with a clear error.

### 3.2 Registry (`src/lib/gwt-registry.js`, generated)
`CMA.registry = { generatedAt, permutation, policyHash, types: { '<type sig>': entry } }` where entry is one of
* `{k:'class', f:[...]}` — field readers in WIRE order including superclass fields (subclass first, then super, as the
  compiled deserializer calls them): each `'i'` int, `'z'` bool, `'s'` string, `'o'` object, `'d'` double,
  `'l'` long, `'b'` byte, `'h'` short, `'f'` float, `'c'` char.
* `{k:'enum'}` — one int ordinal. * `{k:'box', t:'i'|'z'|'s'|'d'|'l'|'h'|'b'|'f'|'c'}` — java.lang boxes.
* `{k:'list'}` (ArrayList, LinkedList, Vector, Stack, HashSet, LinkedHashSet: size + elements),
  `{k:'singleton'}`, `{k:'empty'}` (Collections$Empty*), `{k:'arrays'}` (Arrays$ArrayList: size + elements read in
  instantiate — same reader as list), `{k:'map'}` (HashMap, IdentityHashMap, EnumMap: size + key/value pairs;
  EnumMap instantiate first reads one object (the key class) — represent as `{k:'map', pre:['o']}`),
  `{k:'map', pre:['z']}` (LinkedHashMap reads a boolean first), `{k:'map', pre:['o']}` (TreeMap reads comparator),
  `{k:'set', pre:['o']}` (TreeSet), `{k:'date'}` (long), `{k:'array', e:'o'|'s'|'i'|...}` (length int then elements;
  verified in this build: `[Ljava.lang.String;` elements are read with readString (`o$n`), object arrays with
  readObject (`WZn`), `[D` with readDouble; `[I` does have a deserializer in this build, harmless), `{k:'unknown'}`.
Deserialized values: class → `{$t: sig, f: [values]}`; enum → `{$t: sig, ordinal}`; list/array → JS array;
map → `Map`; date → `{$t, ms}`; box → primitive. Back-reference slots follow GWT's `readObject`: when a positive type index is read, **reserve the next slot
(push null) BEFORE calling instantiate**, then store the instance in that slot, then read its fields. This matters when
instantiate itself reads objects (SingletonList, Arrays$ArrayList, TreeMap/TreeSet comparator, EnumMap): the outer
object gets the lower index. The writer mirrors this (register the object before writing its fields).

`tools/gen_registry.py` (Python 3, stdlib only) reads `tools/bundle/all.js` (concatenation of `<perm>.cache.js` and
all `deferredjs/<perm>/N.cache.js`). Algorithm (proven on 2026-09-27, see `live/analyze_table.py`):
1. constants: `re.compile(r"(?<![A-Za-z0-9_$])[0-9]*([A-Za-z_$][A-Za-z0-9_$]*)='((?:[^'\\]|\\.)*)'")` first-wins
   map var→string (the name anchored at the start of its identifier run — review round 5, §3.5 parser rules).
2. table rows: `a\[(VAR)\]=\[(inst|undefined),(deser|undefined)(,ser)?\]` → sig via constants (601 rows in this build).
3. `fn(name)` extracts a function body by brace matching from `'function '+name+'('`.
4. Classify: sig starts with `[` → array (element kind from the sig: `[I`→'i', `[D`→'d', `[Z`→'z', `[J`→'l',
   `[B`→'b', `[S`→'h', `[C`→'c', `[F`→'f', `[Ljava.lang.String;`→'s' if its deserializer differs from the generic
   object-array one, else 'o'); java.lang.* boxes and java.util.* by name (hard-coded list above); enum if the
   instantiate body matches `/=a\.\$s\(\)|=a\.b\[--a\.a\]/` and `/return [a-z]\[[a-z]\]/`; else class: parse the
   deserialize body statement by statement (split on `;`): `X(b,a.$s())`/`b.p=a.$s()` → 'i'; `a.Xs()`→'z';
   `a.ct()`→'s'; `P8k(a.Ps(),N)`/`S8k(a.Ps())`/`a.Ps()`→'o'; `a.Zs()`→'d'; `a._s()`→'l'; `a.Ys()`→'b'; `a.bt()`→'h';
   `a.at()`→'f' (verify the float reader name if it occurs); a bare call `Name(a,b)` → superclass deserializer:
   recurse and append its fields. Anything unparseable → `{k:'unknown', why}` and print a warning. Also emit the
   reader-method → kind mapping actually found so a future deploy that renames them is detected (`_.$s=function ...`
   lines: `$s`=int, `Xs`=bool, `Ys`=byte, `Zs`=double, `_s`=long, `bt`=short, `ct`=string in this build; the generator
   must derive them from the `l1n`-style reader class each run: find the prototype methods that return
   `this.b[--this.a]` (raw), `i1n(this)` (bool), `j1n(this)` (double), `k1n(this)` (long), `g1n(this,...)` (string)).
5. Write `src/lib/gwt-registry.js` and print stats + a list of unknowns. Must be deterministic (sorted keys).
Also record in the registry: `permutation`, `policyHash` (regex `'app','([A-F0-9]{32})'` on the main cache.js),
`proPolicyHash`, and the `serviceMethods` string list found in the bundle for `com.cronometer.shared.rpc.CronometerService`
(optional, for diagnostics).

### 3.5 Runtime registry rebuild (registry-builder.js + registry-store.js)
Cronometer redeploys often (a new `X-GWT-Permutation` each time) and a deploy may change type CRCs or layouts;
`src/lib/gwt-registry.js` is generated offline for ONE build, so decoding (and the CRCs of the classes we SEND)
break until it is regenerated. The extension therefore rebuilds the registry itself, from the live bundle, on the
page: `src/lib/registry-builder.js` is a line-for-line port of `tools/gen_registry.py` (same bundle → deep-equal
registry, asserted by `tests/registry-builder.html`) and `src/lib/registry-store.js` keeps the result. Both load
right after `gwt-stream.js` (manifest order, mirrored in `tests/load-all.html`).

Parser rules shared by `gen_registry.py` and the port (both must give the same answer; review round 4):
* every inlined reader-helper call (`U0n(a)`, `g1n(a,a.b[--a.a])`, `i1n(a)`, `j1n(a)`, `k1n(a)`) is anchored with
  the lookbehind `(?<![\w$.])`, never `\b` — GWT hands out helper names in sequence (`… Z0n $0n _0n a1n …`) and a
  `$`-initial name is never preceded by a word character at its call sites (`(`, `,`, `=`, space), so `\b` would
  never match it and every class reading through it would become unknown;
* a read to the RIGHT of a `?`, `&&`, `||` or a nested `function` inside a statement is conditional: the type is
  `{k:'unknown', why:'conditional reads in …'}` rather than a class with a guessed layout (a read on the LEFT, as
  in java.lang.Boolean's `return Vho(),a.Xs()?true:false`, is unconditional);
* an enum instantiate is one that reads exactly one int, has no deserializer reads and ends with an index
  expression — `return c[b]` today, `return ($pj(),c)[b]`, `return Xyz[b]` or `return c[b]|0` in a future compile;
* (review round 5) a read inside a statement that starts with `while`, `do`, `if`, `switch`, `try` — or with
  `else`, `catch`, `finally`, which the statement splitter (it cuts after every `}` back at depth 0) delivers as
  statements of their own — is conditional too: `{k:'unknown', why:'conditional reads in …'}`, never a class
  with an extra field;
* the inlined helper BODIES `Number(a.b[--a.a])` and `!!a.b[--a.a]` are typed 'd' and 'z' (a future compile may
  inline them the way it inlines the helper calls today); the bare `a.b[--a.a]` stays int-like;
* word classes are ASCII in both generators: the Python compiles every pattern that uses `\w` / `\b` with
  `re.ASCII`, so a non-ASCII character glued to the reader variable (`b.q='ña'`) is a bare use of it — unknown —
  in both (GWT emits pure ASCII today; the rule keeps the parity);
* the constants pass `NAME='…'` is anchored at the start of each identifier run
  (`(?<![A-Za-z0-9_$])[0-9]*(NAME)='…'`): unanchored, the pass was quadratic in the longest identifier run that
  no constant consumes — a 100 K-char inlined base64 asset cost 4.4 s in V8 and 20 s in Python, anchored it is
  well under a millisecond — and the anchoring is output-neutral because the leftmost match always started at a
  run's first non-digit character anyway.
All of them are output-neutral for build 0A1C16E1…: `gen_registry.py` reproduces `src/lib/gwt-registry.js` byte
for byte and `tests/registry-builder.html` mutates the real bundle to prove each rule.

## 5. Input parsing (parse.js, units.js)
`CMA.parse.lines(text) → [{raw, line, name, qty:number|null, unit:string|null, group:string|null, groupFallback?:[...], part?, customOnly?:boolean, error?}]`.
* Blank lines and `// …` lines are ignored. `## <group name>` always switches the current group; a single-`#` line
  switches it only when its text looks like a group name (one word, or two words with a number or a capitalised
  head: `# Lunch`, `# Group 6`, `# Second breakfast`); any other `# …` line (`# a comment`, `# leftovers from
  yesterday`) is a comment. A quantity-less line ending in `:` (`Breakfast:`) is a header too. Items carry
  `groupFallback` = the earlier headers (most recent first) so plan.js can fall back to the last *resolvable*
  header when the current one is not a real group. `@dinner` / `@Lunch` at the start or end of a line sets that
  line's group (case-insensitive, matched to group names by prefix).
* Search-scope flags (0.3.2, Appendix M): `/custom` (alias `/c`) → `customOnly: true` (search only the user's own
  custom foods / recipes / meals), `/all` → `customOnly: false`; case-insensitive, and only as a whole
  whitespace-delimited token at the START or END of the line body, so `1/2`, `1 1/2`, `salt/pepper`, `w/o`,
  `half/half`, a glued `cheese/custom`, `// …` comments and `@custom` (a group tag) are never flags. Flags and
  `@group` tags are stripped in a loop, in any order (`cheese /custom @lunch`, `cheese @lunch /custom`, `/custom
  @lunch cheese`; one tag per end, a trailing tag wins as before; of several flags the last in reading order wins),
  BEFORE the `Breakfast:` header check, the two-foods split and the quantity parse, so `banana 1 /custom`, `eggs x2
  /custom` and `vitamin c 500mg x2 /custom` keep their quantities and no name contains a flag; `raw` stays the typed
  line. Every segment of a split line carries the line's flag; a flag at the start or end of one segment
  (`mozzarella 30g /custom, banana 1 medium`) applies to that segment only and wins over the line's. On a header line
  (`## Dinner /custom`, `# Lunch /custom`, `Dinner: /custom`, also right before the header's colon: `Dinner /custom:`,
  and in front of it: `/custom ## Dinner`) the flag is stripped before the group name is read and applies to the
  following lines until the next header (a header without a flag ends it); a line's own flag wins. A header with no
  name (`## /custom`, `# /all`) and a line that is only a flag (`/custom`, `/all`) change that scope and keep the
  current group (no item). A flag in front of a `// …` comment is ignored with it. A flag token still inside a food
  name after the quantity parse (`cheese /custom 30g`, `eggs /custom x2`) fails that item with "move '/custom' to
  the start or end of the line" instead of searching the flag as text. `customOnly` is absent without a flag.
  `CMA.parse.stripMarks(text, tags)` is the helper.
* Quantity grammar (anywhere: leading, or trailing after `,`, `:`, `-`, `x`, `×`, or bare at the end): integer, decimal
  (`1.5`, `.5`, `1,5` when no other comma), fraction `1/2`, mixed `1 1/2`, unicode ½ ¼ ¾ ⅓ ⅔. `x2`/`2x`/`×2`.
  A number is a quantity only at a boundary: not followed by a digit or `%` (`2% milk`, `12%` stay in the name) and,
  when a word is glued to it, only if that word is a known unit (`200g` yes, `7up` no).
  Multipliers combine with a size: `2 x 100g yoghurt` / `yoghurt 2 x 100g` → 200 g, `vitamin c 500mg x2` → 1000 mg.
  Two foods on one line, separated by `,` or `;` and each carrying a quantity+unit (`oats 40 g, milk 200 ml`), are
  split into two items with the same `line` and `raw` (`part` 0, 1, …); `rice, 1,5 cups` stays one item.
* Unit = the token right after the number (or attached: `200g`, `100ml`, `2oz`). Known units (normalise, singular):
  g gram grams gr; kg; mg; oz ounce; lb lbs pound; ml milliliter millilitre mL; l liter litre L; cup; tbsp tablespoon;
  tsp teaspoon; slice; piece pc pcs; serving srv; large medium small xl xs; scoop; can; bottle; packet pack; bar;
  each ea; unit; clove; egg? no (food word). Unknown token after the number → not a unit, stays in the name.
* Energy units (0.3.2, Appendix N): `cal cals kcal kcals calorie calories kilocalorie kilocalories`, the spaced /
  hyphenated `kilo calorie(s) kilo-calorie(s) kilo cal(s) k cal(s) k-cal(s)` (any case, so `Cal`) → `kcal`; `kj
  kilojoule kilojoules kilo joule(s) kilo-joule(s)` (`kJ`) → `kj`. They are ordinary quantity+unit pairs wherever a
  quantity is recognised (leading, trailing, mid-line, after `,` `:` `-`, glued `300cal` or spaced `300 cal`, and —
  for energy units only — hyphenated `300-cal`; multipliers `2 x 150cal bar` → 300, split lines `almonds 300cal,
  banana 1 medium`, decimal comma, fractions); whole tokens only (`calzone 2`, `2 calzones`, `calamari 100g`, a
  bare `cal` are not energy). The two-word spellings are tried before one word, so `300 kilo calories` is not 300 kg.
  Before an energy word, `N,NNN` groups are a thousands separator (`1,250 kJ` → 1250, `2,000 kcal` → 2000; also a
  no-break / thin space), not the decimal comma they are elsewhere (`300,5 kcal` stays 300.5, `0,250` stays 0.25);
  the same groups with a plain space (`almonds 1 250 kJ`, `2 150cal bars`) are an error that names both readings
  ('write 1250 kJ …, or 1 x 250 kJ for a count'). A dot is always a decimal point (`1.250 kJ` = 1.25 kJ; §5.3 flags it).
  `item.qty` stays the typed number and `item.unit` is `'kcal'` or `'kj'` (no parser conversion: the preview shows
  what was typed; units.js divides kJ by 4.1868). Deliberately, a number right before an energy word is always an
  amount: `100 calorie pack almonds` is 100 kcal of "pack almonds". `0 cal soda` is 'invalid quantity' like any 0.
* Name = remaining text trimmed of separators. Examples that must parse (tests):
  `200g chicken breast`→200,g,"chicken breast"; `chicken breast 200 g`; `chicken breast, 200g`; `Chicken breast - 200 g`;
  `2 large eggs`→2,large,"eggs"; `2 eggs`→2,null,"eggs"; `eggs x2`; `1 1/2 cups rice, cooked`→1.5,cup,"rice, cooked";
  `½ cup oats`; `banana`→null,null,"banana"; `3 tbsp olive oil`; `100 ml milk`; `1 slice bread`; `0.5 kg potatoes`→500,g;
  `## Dinner` (group line); `salmon 150g @lunch`; `1.5lbs mozzarella cheese /custom`→1.5,lb,"mozzarella cheese",customOnly;
  `300cal almonds`→300,kcal,"almonds"; `almonds 1250 kJ`→1250,kj,"almonds".
### 5.3 Measure matching (`CMA.units.pickMeasure(measures, unit, qty, opts)`) →
`{measure, quantity, grams, note}`; measures as returned by `CMA.rpc.measuresOf`.
* **No unit typed** (quantity q or none) — `CMA.units.defaultMeasure(measures, {hitMeasureId, defaultMeasureId})` first
  resolves the measure the row starts on: the search hit's measureId when it is in the list (the measure the search row
  described to the user, '1 breast - 172g'), else the food's own default (FoodMeasures.f[0]: `m.isDefault` from
  `rpc.measuresOf`, or `opts.defaultMeasureId`, which plan.js passes from `foodDefaultMeasureId`), else the plain 1 g 'g'
  measure (`mpj`: amount 1, 1 g per unit, named 'g'), else the first measure in wire order. Every step resolves only
  over VISIBLE measures (`hidden` false; `VCe` drops hidden ones before `TCe` runs), and `suggestMeasure` never offers
  a hidden one; a typed unit may still match one. Then `units.pickDefault`:
  a) the default is not a bare gram/ml unit (`units.isGramOrMlUnit`: a name that denotes g or ml — 'g', 'gram', 'grams',
     'ml', 'milliliter') → q or 1 of it; this includes a food whose only measure is such a measure ('scoop', a Recipe
     'serving'); the hit measure being the plain 'g' is no exception, the rule looks at the resolved default;
  b) the default is a bare gram/ml unit and other measures exist → `{error: "no unit given and this food's default unit
     is grams — pick a unit", measure, suggested}` (status needs-choice, 'millilitres' for an ml default). `measure` =
     `suggested` = `units.suggestMeasure`: the f[0] default when it is not gram/ml, else a measure whose name carries a
     count word (serving, piece, bar, medium, large, small, each, unit, slice, scoop, whole, item, portion, package,
     container, bottle, can), else the first Atomic/Recipe measure, else the first non-gram/ml measure. The panel's
     existing `Use <measure>` button offers it; `repick`/`withMeasure` keep the typed quantity as a count of it (no unit
     was typed, so `convertQuantity` is not involved);
  c) every measure is gram/ml-like (a lone 'g', 'g' + 'milliliter') → 100 g like the dialog when q is absent (note 'no
     unit given; using 100 g like the app'), else q grams (note 'no unit given; N taken as grams'); an ml-only food the
     same way with 'ml' / 'millilitres'. The amount is sent through the measure's own size: quantity = (q or 100) /
     grams per unit (ml default: Measure.f `ml`, else its shown amount — never its grams, which carry the density),
     so a 'g'-named measure that is not 1 g per unit (the getFood fallback `measuresFromHit('100 g - 100g')`: name 'g',

    food without f[0] would start on 'lb'): a gram default is asked about instead;
  - the amount is `MCe(null, j)`: **100** when j is the plain 1 g 'g' / 1 ml 'ml' (`b.a==1&&b.k==1&&_ko(b.g,'g')`, a

    text) without firing any event, so `TBe` (`MeasureSelector/lambda$2` `_.Ne`, registered by `dCe` as

  - `hte` (after `UBe`) restores the last serving of that food from the `mze` cache (measure `Mjj(food, h.n)`, amount

* `CMA.units.convertQuantity(qty, unit, measure)` → `{quantity, note}` | null: the amount of `measure` equal to
  `qty` of the typed `unit` when that is safe (same unit; mass → a non-recipe measure with grams; volume → a
  measure with ml or a known volume-unit name; a word unit the measure name contains), null otherwise — a typed
  gram/ml quantity must never become the COUNT of a recipe measure. The panel uses it when a needs-choice row
  gets a measure picked by hand, resetting the count to 1 with a note when it returns null.
* No unit, qty → the same rule with quantity q (a: q of the default; b: needs-choice; c: q grams, noted).
* Mass unit (g/kg/mg/oz/lb) → grams = qty converted to g (oz 28.3495, lb 453.592). Prefer a measure named exactly
  `g` (or `gram`); else any Weight measure with grams>0 (quantity = grams/measure.grams, note 'shown as <name>');
  else the default / any non-recipe measure with grams>0 the same way. When only recipe-like measures remain (the
  wire amount of a Recipe measure or the weightless 'full recipe' is a COUNT, `Rqj`): a Recipe measure with grams>0
  is converted to a count (note 'converted to N × <name>'), otherwise `{error:'no weight measure for this recipe'}`
  (needs-choice) — never the gram total as the quantity.
* Volume unit (ml/l/cup/tbsp/tsp/fl oz) → find measure whose normalised name starts with the unit (`cup` matches
  `cup`, `cup, chopped`); `ml`/`l` match `ml`/`milliliter`; else any Volume-type measure: convert via ml (cup 240,
  tbsp 15, tsp 5, fl oz 29.57) if the target measure's name is a known volume unit; else `{error:'unit not available'}`
  so the panel asks the user to pick.
* Other unit words (large, slice, serving, piece...) → measure whose normalised name equals / starts with / contains
  the word (in that order); `{error}` if none.
* Always return `grams = quantity × measure.grams` for Weight/Volume/Atomic (the raw double product, unrounded, as
  the dialog's `Nqj`); for Recipe type grams = quantity.
* **Calorie amounts** (0.3.2, Appendix N) never go through `pickMeasure` (it refuses `kcal` / `kj` with an error, and
  `convertQuantity` returns null for them, so a measure named '…cal…' can never receive the number as a count):
  `CMA.units.pickEnergy(measures, energyValue, targetKcal, opts)` → `{measure, quantity, grams, note, kcal,
  kcalPerUnit, warn}` | `{error, refused?}`, with `energyValue` = `CMA.rpc.energyKcalOf(food)` and `targetKcal` =
  `CMA.units.energyToKcal(qty, unit)` (kJ ÷ 4.1868, `KJ_PER_KCAL`).
  - kcal per ONE of a measure is the Add Food dialog's `Rrj` (`CMA.units.kcalPerUnit(m, value)`, k = `grams`): a
    Recipe-type measure → `value / k` (0 when k is 0); a weightless Weight measure (k 0, the 'full recipe') → `value`;
    anything else `value × k / 100`. `Measure.a` plays no part. quantity = target / perUnit, exactly what Cronometer's
    own diary Calories-cell edit computes (`j2i`, which does nothing when perUnit is 0), so the diary shows the target
    for the entry; grams = `gramsFor(measure, quantity)` like any pick (6-decimal quantity, unrounded product).
  - Measure: `opts.measureId` (the panel's Unit dropdown) when given, refused with `{error: "'handful' has no weight to
    put calories on — pick another unit", refused}` when it carries no energy; else the SAME default a unit-less line
    starts on (`defaultMeasure` with `{hitMeasureId, defaultMeasureId}`), where a bare gram default is fine (the amount
    is exact whatever the measure, so no needs-choice). A measure "carries energy" when perUnit > 0 and it is
    recipe-like or has grams > 0; if the default does not (a weightless Volume / Atomic / Recipe measure, a weightless
    Weight measure other than 'full recipe'), the plain 'g', then any Weight measure with grams > 0, else `{error: 'no
    measure with a weight to put calories on'}`. Hidden measures are skipped as in `defaultMeasure`.
  - Typable: a measure is used only when its quantity survives the Add Food dialog's amount box (6 characters, 3
    decimals: `formatQuantity`): > 0 at 3 decimals, below 1,000,000 and within 5 % of itself there
    (`ENERGY_TYPABLE_SHARE`), so the UI engine types what the RPC engine would send. The default path takes the
    next candidate above that is typable (3 kcal of a 2,000 kcal 'full recipe' is 0.0015 → typed 0.002 → its 'g'
    instead); when none is, or the picked `measureId` is not, `{error: "0.1 kcal is too small an amount of 'serving'
    to add — pick another unit", refused}` (needs-choice; 'too large' above the limit).
  - Errors (the row is not added): energy null / 0 / not finite → 'no calorie data for this food'; `opts.meal` →
    'calorie amounts are not supported for meals (Cronometer adds a meal whole)'; a target ≤ 0 → 'invalid quantity'.
  - Note: `'300 kcal → 1.83 oz (51.8 g)'`, `'300 kcal → 51.8 g'` on the plain 'g', `'250 kcal → 0.5 × serving'` for a
    recipe count, `'1250 kJ (298.6 kcal) → …'` with `opts.kj`. Above 1000 g (`ENERGY_SANITY_G`; recipe counts
    excepted) the note adds '— over 1 kg: check the food and the number', below 5 kcal (`ENERGY_SANITY_MIN_KCAL`: a
    `1.250 kJ` meant as 1250) '— under 5 kcal: check the number'; either sets `warn`, and the row stays ready.

## 6. Plan (plan.js) and RPC engine (engine-rpc.js)
`CMA.plan.build(session, items, opts, progressCb) → plan = {rows, date, groups, defaultGroupId, positionsSource:
'getDayInfo'|'fallback'|null, nextPos, warnings:[], stopped:null|'session', builtAt}` where each row is
`{index, item, hits:[...], hit (chosen), hitIndex, food (Food value)|null, measures:[...], pick:{measure, quantity,
  grams, note}|{error}, translationId, customOnly, groupId, groupName, groupNote, position, order,
  status:'ready'|'needs-choice'|'error', message, result?}`; opts = `{groups, defaultGroupId, date, searchDelayMs=300,
retryMs=2000, maxHits=10, maxResults=50, positions=true, customOnly=false, unverified, sessionProvider, now,
isCancelled}` (groups and date default to `CMA.capture.state`). Rows never store the session (nothing the
diagnostics view may serialise carries the nonce).
* Custom-only search (0.3.2, Appendix M): each row's scope is `item.customOnly != null ? item.customOnly :
  opts.customOnly` (the panel passes Settings → *Search only my custom foods*; only an explicit `true` counts) and is
  stored as `row.customOnly` on every row (also rows that are never searched: engine-ui reads it). searchFoods gets
  `{maxResults, customOnly}`; for a custom-only row the hits are filtered to `CMA.plan.isCustomHit` (source 'Custom' or
  none) BEFORE the maxHits slice, and an empty result is "no custom food matches" (unverified mode: the reason
  "unverified (UI engine): no custom food matches") instead of "no results".
* A quantity-less item whose name equals a group name (`Breakfast`) is not searched: status 'error' with the hint
  "looks like a group header — write '## Breakfast' to switch groups".
* Search each item sequentially (300 ms apart; one retry after 2 s on network error). Choose hit: exact
  case-insensitive name match on `name`, else the first hit (server score order). Keep up to 10 hits for the dropdown.
* Fetch `getFood(hit.id)` for the chosen hit. When getFood answers but the Food cannot be used (kind 'decode' /
  'rpc' / 'http' / 'incompatible' / 'notfound', not session/network/throttled) the row falls back to the measure the
  hit describes (`measureDisplayName` `'1 breast - 172g'` → `[{id: hit.measureId, name:'breast', grams:172, amount:1,
  fromHit:true}]`, `CMA.plan.measuresFromHit`), keeps `hit.translationId`, stays 'ready' with the note
  "measures from the search hit only (getFood failed: …)" and logs the error to capture.log; without a parsable
  description the row is an error. (Also when the user changes the hit in the panel →
  `CMA.plan.rechoose(session, row, hitIndex)`: the session comes first because getFood needs it and rows do not
  store it). Other panel edits: `CMA.plan.repick(row, measureId, qty)`, `CMA.plan.reposition(plan, row, groupId)`
  (next free position of the new group), `CMA.plan.assignPositions(session, plan)` (the panel re-runs it right
  before Add all so entries added by hand in between do not collide).
* Serving/Day type signatures used by `servingFor` are resolved through `CMA.gwt.SIG` (registry) with the build's
  literals only as a fallback for pages that do not load gwt-stream.js.
* Group: item.group name → match enabled group by case-insensitive prefix; else each name of `item.groupFallback`
  (earlier headers, most recent first; note "group '…' not found, using X (previous header)"); else the panel's
  default group (opts.defaultGroupId). Default group rule when the panel first opens: hour 4–10 Breakfast(1),
  10–14 Lunch(2), 14–21 Dinner(3), else Snacks(4) — mapped to the first enabled group with that id, else the first
  enabled group.
* Positions: before adding, `getDayInfo(session, date)`; for each enabled group compute
  `maxPos = max(order & 0xFFFF)` over Servings whose `(order>>16) === groupId`; a new entry gets `maxPos+1`,
  incrementing per row in the same group. If getDayInfo fails, fall back to `pos = 1000 + rowIndex` and log it.
  Known divergence from the dialog (`qvd`, serving-fields-resolved.md §3): the UI walks EVERY DiaryEntry of the day
  (exercises, biometrics and notes share the packed `group<<16|position`) and returns a same-group TIMED entry's
  own position unchanged; we count Servings only, so a position may collide with a non-food or timed entry. The
  client only sorts by it (`m1i`/`UYi`) — a fidelity gap, not a failure; the order slot of the other entry
  classes is not resolved in the registry.
* Unverified mode (`opts.unverified`, set by the panel for the UI engine): when no session is captured
  (`session.userId` missing) or when search / getFood fail or find nothing, the row stays 'ready' with
  `unverified:true`, `hit` (kept when the search worked) and `pick = {measure: item.unit ? {name: item.unit} :
  null, quantity: item.qty || 1, grams: null, note:'unverified (UI engine): <why>'}`; `servingFor` throws for such
  rows and engine-rpc skips them ("unverified row (UI engine only)").
* Calorie amounts (0.3.2, Appendix N): an item whose unit is `kcal` / `kj` (`CMA.plan.isEnergyItem`) is picked by
  `units.pickEnergy` over the loaded Food (`rpc.energyKcalOf`; the getFood reply every row already fetches — search
  hits carry no energy, so there is no extra request) with `{hitMeasureId, defaultMeasureId, meal, kj}`; meal =
  `hit.type === 'MEAL'` or `rpc.foodTypeOf(food) === 'MEAL'` (`CMA.plan.isMealRow`). A refused measure (`{refused}`:
  picked without a weight, or not typable) is needs-choice, every other refusal is 'error' (no diary position is
  reserved). Without the Food — the getFood
  fallback to the hit's measure, or an unverified UI-engine row — the row is an error "calories need the food's
  details, which could not be read (<why>); type an amount such as 50 g instead": the typed number is never sent as
  a count of the hit's measure or typed into the dialog with a 'kcal' unit. `repick(row, measureId, qty)` on such a
  row takes `qty` as the new target in the typed unit (`row.item.qty`) and `measureId` as the measure to carry it
  (null = the default again), so the Unit dropdown keeps the calories and no path turns them into a count;
  `rechoose` recomputes from the new food. Engines: the RPC engine sends `pick.grams` / quantity like any pick; the
  UI engine selects `pick.measure` and types `pick.quantity` (≤ 3 decimals, `formatQuantity`; pickEnergy plans only a
  quantity that survives that, and the engine never types a 0, §7 step 6).
### 6.4 `CMA.engineRpc.run(session, plan, opts, progressCb) → {added:[{row, servingId, serving, message?}], failed:[{row, error, kind}], skipped:[{row, reason}], stopped:null|'session'|'cancelled'|'decode', lastBatch, refresh}`
`opts = {delayMs=250, retryMs=3000, throttleMs=5000, refresh=true, refreshOpts, isCancelled, sessionProvider}`; only
rows with `status === 'ready'` are sent; `progressCb({phase:'adding'|'row'|'retry'|'throttled'|'refresh'|'done',
index, total, row, ok?, servingId?, message?})`. `opts.sessionProvider` (a function, the panel passes
`CMA.capture.session`) is re-read before every request in `run`, `undo` and `plan.build` so a nonce rotated by
the app's `reauthenticate` during a long batch is used from the next row on; `session` is the fallback snapshot
and names the batch owner. An updateDiary `//OK` the registry cannot decode (rpc error with `.applied`) means the
server DID add the entry: the row is pushed to `added` with `servingId: null` and a `message` ('added; the reply
could not be read (registry stale) — no undo id'), `row.result = {ok:true, servingId:null, message}`, and the
batch stops with `stopped = 'decode'` (remaining rows 'not attempted (decode)') — every further add would end the
same way and a "failed" verdict would steer the user into duplicates; the panel adds a check-the-diary notice.
Sequential, `opts.delayMs` (250) between rows, one automatic retry after 3 s on network errors that cannot have
reached the server (`Failed to fetch`, empty 502/503); a **timeout is never retried** (the request may have been
processed — re-sending could add the food twice): the row fails with kind 'timeout' and "check the diary before
re-adding". Never retry a `//EX` or a 4xx/5xx that carries a body (non-idempotent). Stop the batch on
`CMA.errors.Session`. After the batch, refresh the diary (§6.5) and store `{date, servingIds, at, userId}` as
`lastBatch` in memory + `chrome.storage.local` (ids, date, timestamp and the account id — the panel offers Undo
only to that account and only for 24 h).
`CMA.engineRpc.undo(session, lastBatch)` → `{removed:[ids], failed:[{id, error, kind}], dropped:[ids], stopped,
refresh}`: removeServing for each id (the base64 string, verbatim), sequential. Ids whose removal the server
rejected (kind 'rpc' / 'rejected' / 'http' / 'incompatible', e.g. already deleted by hand) are `dropped` from the
remaining batch; network / throttle / session failures keep theirs; an empty remainder clears the stored batch.
`lastBatch` lives in memory and under `chrome.storage.local['cmaLastBatch']`. A throttled add is retried once after the 5 s back-off
only when the error says the request was rejected (HTTP 429 / retryable); a throttle-version change alone is never
retried because the add may have gone through.
Since 0.3.0 a run that added entries (incl. the rows counted as added after an unreadable `//OK`) and an undo that
removed some each emit ONE `CMA.events` `'diary-write'` `{method: 'updateDiary'|'removeServing', ok: true, days:
['YYYY-MM-DD'], count}` at the end (the plan / batch date as ISO, built from its parts): the engine sends with
`fetch`, which the page hook never relays as an `'rpc'` event, so this is how the Adaptive TDEE data layer (§12.4)
learns which day to read again. No ids, no foods; a throwing listener never breaks the batch (`tests/unit.html`).
### 6.5 Diary refresh
The app updates its diary only from its own `updateDiary` responses, so after out-of-band adds:
1. click `.diary-date-previous` (an `<i>` inside the date nav; the first VISIBLE one inside `.diary-panel`, since
   the hidden ClientDiaryDate panel uses the same class), wait 1200 ms, click `.diary-date-next`, wait 1200 ms
   (each triggers `getDayInfo`); verify by watching the hook for a `getDayInfo` for the target date;
2. if the elements are missing OR the clicks were not verified: set `location.hash='#dashboard'` then `'#diary'`
   after 300 ms (always `#diary`: the entries went to the diary, restoring `#foods` would never reload it); the
   result is `{method:'nav'|'hash'|'none', verified, clicks, hashFlip?:true}`;
3. always offer a "Reload page" button in the results view, and when `refresh.verified` is false append "the
   diary did not confirm the refresh: press Reload page to see the new entries" to the run/undo summary.

## 11. Packaging and Chrome Web Store listing (tools/build_zip.py, STORE-LISTING.md, PRIVACY.md)
`python tools/build_zip.py [repo-root] [--out DIR]` writes `dist/multi-add-for-cronometer-<manifest version>.zip`
holding exactly `manifest.json`, `popup.html`, `LICENSE`, `icons/*.png` and `src/**/*.js` (tests, tools, the docs,

names every script the extension runs, so an unreferenced `src/` file is a leftover and fails the build); no

test. Exit 0 only on `PACKAGE OK`. The archive is written under a temporary name (`….zip.tmp`), verified, and
renamed to the release name only when every check passed — a stale package under the release name is removed
first and a failed build deletes the temporary file, so `dist/` never holds a broken zip under the name a good
build produces (review round 5). Run `tools/check_manifest.py` and `tests/run.sh` first and
rebuild the zip after ANY change to `src/` or `manifest.json` (it snapshots the tree). The 0.3.2 package (like 0.3.1)

repository URL) and an optional 32 px icon (16/48/128 required, any other size fails) and requires a description of

## 12. Adaptive TDEE (src/tdee/, src/ui/tdee-view.js) — since 0.3.0

An optional second feature: a MacroFactor-style estimate of the user's real energy expenditure from the intake and

DATA-LAYER RECIPE), tdee-critic.md, tdee-intake-burned.md, tdee-weight-history.md and tdee-integration.md (untracked,

### 12.2 The reads (rpc.js §4), capture and the optional registry check
Five read-only RPCs that the web app itself sends: the dashboard's *Energy History* card (`QHc`,
getCaloriesConsumedAndBurned), the profile weight history (`BiometricHistoryHandler`, getBiometrics with null Days),
the diary calendar (getCalendarInfo), the Nutrition Report's *All Time* range (getFirstDayWithData) and the
preference reader `bOf` (getPreference). Signatures, bodies and return shapes are in §4.
* **Energy rows** (getCaloriesConsumedAndBurned, `last` EXCLUSIVE, one `double[12]` per day, ascending; the layout
  is read from the dashboard's MiniGraph `PHc`, whose modes are `'Consumed,Burned,Net,Combined'`;
  research/tdee-critic.md 1): `[0]` consumed kcal; `[1]` exercise kcal, NEGATIVE on the wire (the card negates it
  and stacks it as 'Exercise'); `[3]` BMR; `[4]` TEF, always sent, but the CLIENT adds it only when the preference
  `use.thermic.effect.food` is `'true'`; `[9] + [10]` activity; `[11]` a server-computed 'Net' of unknown formula
  (unused); `[2]` and `[5]`–`[8]` are never read by the client. Wire values are kcal for every account (the app shows
  kJ as kcal × 4.1868). **burned = `[3] + [9] + [10] + |[1]|`, plus `[4]` when the preference is 'true'; `[1]`
  alone is never "burned".**
* **Weigh-ins** (getBiometrics): Weight = metric 1, kg = unit 1 (the server converts into the requested unit; lbs 2,
  stone 68524); null Days = the whole history in ONE call; a range includes its `to` day; Times null and DayQueryType
  All (ordinal 0) as in every call of the app. `DataPoint = [o Day, o Time|null, d value]`.
* **Logged / complete flags** (getCalendarInfo): `CalendarDayInfo = [z complete, o Day, o fastFinish, o fastStart,
  o follicular, z loggedBiometric, z loggedExercise, z loggedFood, z loggedNote, o luteal]`; a day absent from the
  list has nothing logged (the diary calendar's own reading).
* **Preferences** (getPreference, response kind `'s'`): `use.thermic.effect.food` (app default 'false'),
  `units.calories` ('true' = kcal, also the default when absent), `weightUnit` ('Kilograms' | 'Pounds' | 'Stone',
  default Pounds). Only TEF changes a number; the other two only choose the display units.
* `CMA.gwt.BASES` / lazy `SIG` getters: DAY_QUERY_TYPE, DATA_POINT, DATA_POINT_ARRAY, CALENDAR_INFO,
  CALENDAR_DAY_INFO, DOUBLE_ARRAY (`[D`), DOUBLE_ARRAY_2D (`[[D`). No registry work was needed: the shipped registry
  already decodes every one of these types.
* capture.js: `USER_ID_PARAM` gains getCaloriesConsumedAndBurned, getCalendarInfo, getBiometrics and
  setUserPreference (param 1); the `'rpc'` event of a captured `setUserPreference(String, int, String key, String
  value)` carries `pref: {key, value}`; the log names the key (`prefKey`), never the value (weightInKG and heightInCM
  are body data).
* registry-builder.js: `OPTIONAL_LAYOUTS` (DataPoint `ood`, DataPoint[] `array:o`, CalendarInfo `o`,
  CalendarDayInfo `zoooozzzzo`, DayQueryType `enum`, `[[D` `array:o`, `[D` `array:d`) and `OPTIONAL_METHODS.tdee`
  (the five methods) are checked by `checkOptional(registry, 'tdee')` → `{ok, problems, checked}` and reported by
  `validate()` as `optional.tdee`. They NEVER change `ok` / `problems`: a deploy that drops or reshapes a type only
  the TDEE tab reads turns its sync off ("TDEE sync unavailable: …", gate code `layouts`) and leaves the multi-add
  engines and the decoder rebuild alone. Day `bbh` and Time `bbb` stay core layouts.

`CMA.events` `'tdee-data'` `{type: 'status'|'data'|'error', status, error?}` follows every change. The data layer
listens to `'rpc'` (the app's writes, setUserPreference), `'diary-write'` (the RPC engine's own writes, §6.4),
`'state'`, `'registry'` and `'registry-progress'`, and to `chrome.storage.onChanged` (other tabs, below).
**Other tabs.** Every open Cronometer tab runs its own copy of the data layer over ONE `chrome.storage.local`, and
tabs may be logged in to DIFFERENT Cronometer accounts. `chrome.storage.onChanged` reports every change to every tab,
the writer's own included: each write is remembered per storage key name (canonical JSON with sorted keys, because
Chrome reports stored dictionaries with sorted keys) until its echo comes back, and a key that already holds the same
value is not written again. A tab acts only on the loaded account's OWN keyed entries (`<base>:<userId>`): another
account enabling, syncing, disabling or deleting in another tab (or in this tab before an account switch) never
affects it - those events only update the `otherAccountsStored` count, and a value under this account's key that
carries another userId is never adopted. What another tab of the SAME account wrote is adopted at once:
`cmaTdeeSync:<userId>` removed (Delete TDEE data) → this tab cancels its work and drops its memory copy (as
`disable({forget})` does locally), and removes again any key of this account its own write was still carrying (that
write lands after the deletion); `enabled` false (Disable) → the tab stops (and re-asserts it after its own in-flight
write); any other key of this account → adopted (days keep the windows this tab merged but has not written yet),
unless this tab's own newer write to that key is still on its way. A legacy (un-suffixed) key is acted on only while
this tab runs on this account's legacy copy (its keyed slot holds nothing because the migration copy could not be
written): its removal is then another tab's Delete TDEE data. As a second check, `execute()` reads
`cmaTdeeSync:<userId>` (and this account's legacy `cmaTdeeSync` while it has not been copied) before a job's first
request and sends nothing when the stored consent for this account is gone (the event may not have arrived, or the
listener could not be added). Without `onChanged` the echo bookkeeping is off: every write is sent and only the
second check applies. **Account switch in one tab** (capture `userId` changes): the running job is cancelled (it
merges and writes nothing more), the new account's keyed records are loaded (migrating its legacy records), and the
previous account's keys stay exactly as they are.
Settings: `{goal: {ratePctPerWeek}, sex 'female'|'male'|'other' (the calorie floor only), checkInWeekday 0–6
(0 = Sunday, default 1 = Monday), responsiveness 'stable'|'balanced'|'responsive' (engine drift 10 / 15 / 25),
manualInitialKcal|null (500–10000 stored; the view accepts 800–8000), proteinGPerKg 1.6|1.8|2.2, fatShare
0.25|0.35|0.5, activityAware false, units {weight 'auto'|'kg'|'lb', energy 'auto'|'kcal'|'kJ'}, modelStartDate|null,
trustCompleteOnly false, goalChangedAt|null, nudges {weighIn?, partial?: 'YYYY-MM-DD'}}` — `nudges` holds the view's
dismissed data-quality nudges (hidden until that check-in week). A check-in: `{date, accepted, targetKcal,
expenditureKcal, sdKcal, trendWeightKg, ratePctPerWeek, macros {proteinG, fatG, carbsG}, notes, at,
previousTargetKcal, goalChanged, goalRatePctPerWeek}` — `goalRatePctPerWeek` is the goal the user had chosen
(`ratePctPerWeek` is the engine's capped rate), so a goal changed and changed back is no goal change (§12.7).
Record assembly (TDEE spec §2), one record per calendar day from the first stored day to today:
* **intakeKcal**: row[0] > 0 → row[0], whatever the calendar says (energy consumed means food was logged; a day
  missing from an incomplete or silently capped calendar reply must not drop a real intake); row[0] = 0 →
  CalendarDayInfo.loggedFood true → 0 (a logged fasting day), else null (nothing logged: never 0, also without
  calendar flags); a CSV value counts as logged. **Today's intake is always null**, today being the LOCAL calendar
  date from `CMA.capture.today()`: never `capture.state.diaryDate` (the day the diary SHOWS) and never
  `toISOString()`.
* **weightKg**: the first weigh-in of the day = the smallest Time; untimed points rank after timed ones, stable in
  wire order (the app itself keeps the LAST point of a day; the TDEE spec wants the first); values ≤ 0 are dropped;
  the engine's 4-SD rule handles typos.
* **burnedKcal**: the §12.2 formula from the stored parts with the CURRENT TEF preference (a preference change needs
  no request); null when ≤ 0, not finite, or before firstDay (pre-account zero rows must never reach the prior).
  `dayList()` keeps today's (partial) figure for the History; **`records()` passes null for today**: TEF follows the
  food logged so far and exercise / tracker syncs arrive later, and the engine averages burned into its warm-up prior
  (the first 7 non-null values from the first weigh-in: on a reset day that would be today's partial value alone) and
  into `cronometerBurned14Kcal` / the calibration ratio. (The recipe's "only activityAwareDailyTarget uses today's"
  was wrong; the view reads today's burned from `dayList()` for its activity-aware line.)
* **excluded**: override true ('user') > override false (confirmed: beats every automatic rule) > trustCompleteOnly
  (opt-in) with complete false ('incomplete') > the partial-day heuristic ('partial'). **`complete` alone never
  excludes**: most users never press *Mark day as Complete*, and the engine turns an excluded day into a missing
  nutrition day. The heuristic (TDEE spec §2.3; its parameters are ours): a logged day below 50 % of the median of
  the previous 14 logged days, needing at least 7 of them within the last 60 calendar days, excluded "until the user
  confirms" (TDEE spec §2.3): only days that count as fully logged feed later medians - a flagged day stays out until
  the user answers "Yes, I ate little" (override false), so a run of under-logged days never lowers the median by
  itself and never reaches the engine unconfirmed; a deliberate new cut is flagged until about a week of it is
  confirmed; user-excluded days never count; `partialSuspect` drives the view's "Fully logged?" prompt until the
  user answers.
* `records()` passes only days on or after modelStartDate (the TDEE spec §5 reset); today is always included.

### 12.4 Sync policy
* **Consent first**: no request before `enable()`. The first full sync reads months of health data; PRIVACY.md says so.
* **Gate before EVERY call**, and a reply that arrives after a block appeared is dropped: the account is known and
  its records loaded; enabled; `CMA.capture.ready().ok`; no `state.registryMismatch`; no decoder rebuild in flight
  (`CMA.registryStore.inFlight()`); the five rpc functions exist; `checkOptional('tdee')` passes. Codes: no-account,
  loading, capture-not-ready, decoder-mismatch, decoder-rebuilding (transient: the request is parked and runs once
  the block clears), not-enabled, rpc-missing, layouts. Cached data stays visible meanwhile.
* Calls are sequential, at least 250 ms apart, each with a fresh `CMA.capture.session()` (the app may rotate the
  nonce); Throttled backs off once (`CMA.rpc.throttle.backoffMs`) and retries, a network error retries once, Session
  and incompatible stop the job; an //EX, HTTP or decode refusal is handled by the phase. An account switch or
  `disable()` cancels a running job, which then merges nothing and never serves or blocks new work.
* **Full sync**, in order: getFirstDayWithData (null → today − 548 days; refused → the first day an earlier sync
  learned, the fallback only when none is known; clamped to 5 years) → the three preferences (one refusal stops the
  others: what was never read stays unknown, TEF assumed off, `prefs.assumed`) → getBiometrics for the whole history
  (points older than 5 years dropped), then getBiometrics for the recent 92 days by an explicit range (`BIO_RECHECK_DAYS`),
  whose answer is authoritative inside that window: live on 2026-09-28 the whole-history answer held one weigh-in day
  fewer than the ranged query the delta syncs use (13 → 12 stored days right after a weigh-in was added), so a full
  refresh dropped it. Disagreements inside [today − 91, today] are noted with dates only (`weigh-in check: …`); when only
  the ranged call works, only its window is replaced; when only the whole-history call works, it is used for the whole
  history as before, with a `recent weigh-in check unavailable` note → getCaloriesConsumedAndBurned from max(firstDay, first weigh-in − 14 days)
  (today − 27 days while there is no weigh-in) to today, in windows starting at 92 days: a row count ≠ span, an //EX
  or an HTTP error halves the window actually sent (`min(size, span) / 2`, floor 28: a short last window is never
  resent unchanged, and a window of 28 days or less is marked unavailable at once; a decode error is not retried
  smaller); the largest window that returned exactly `span` rows is kept as `energyChunk`, but not after an HTTP
  error in that phase (a transient 500 must not shrink every later sync); three unavailable windows in a row end the
  phase (listed in `diagnostics().energyUnavailable`) → getCalendarInfo over the same span in 42-day chunks that
  request `[a, b + 1]` (a superset whether the server's end is inclusive or not; only days inside the chunk are
  mapped); refused → the flags of the uncovered part are cleared (a stale "nothing logged" must not hide intake) and
  `flagsSource` is 'none'. At its end a full sync drops the days older than the 5-year window that came from
  Cronometer (they are never read again; CSV days stay). A full sync writes `cmaTdeeDays` after each phase (a long
  backfill keeps its progress); a shorter job writes it once, at its end. A completed sync clears `lastError`; what
  it could not read goes to `notes`.
* **Merge**: a fetched window REPLACES every day inside it (empty days are written as nulls, so deletions
  propagate); days outside are untouched; a CSV value survives only where the RPC returned nothing for that field.
* **Delta** (the view calls `sync()` when it opens): the last 14 days of all three reads — backdated edits and
  device syncs (Fitbit, Garmin, Withings, Oura …) write server-side with no client RPC — at most every 10 min unless
  `force`; a full sync instead when the last one is older than 7 days or ROW_LAYOUT_VERSION changed; a running full
  sync serves any request.
* **Dirty days**: a successful app write seen as an `'rpc'` event (updateDiary, editDiaryEntries, editServing,
  removeServing, clearDay, copyDay, logRepeatItemsForDay, addBiometric, editBiometric, removeMeasurement,
  addExercise, editExercise, removeExercise, setDayComplete) or a `'diary-write'` event from the RPC engine marks
  every Day inside its parameters (or its `days`) and today; the viewed day only when the write names no day itself
  (removeServing, removeMeasurement, removeExercise, logRepeatItemsForDay and the other id-only writes edit the day
  the diary shows) - a stale viewed day must not widen a refetch to years; debounced 30 s (every write re-arms it:
  a meal logged item by item is one refetch, not three requests per item; today's own food never reaches the model),
  then `[min − 1, today]` is read again. A captured setUserPreference of a TEF / unit key is applied without a request; bmr,
  calories.activity, calories.activity.custom, weightInKG and heightInCM schedule an energy-span resync.
* `ROW_LAYOUT_VERSION` (1): bump it when a live-verified correction changes what a stored row means; stored days are
  then read again by the next (forced) full sync.

### 12.5 Storage (chrome.storage.local; PER ACCOUNT: key `<base>:<userId>`, every value `{userId, …}`)
* **Per-account keys** (since the live bug of 2026-09-28: in 0.3.0 the five keys held ONE account for the whole
  browser, so a second account - a reviewer's test account - that pressed Enable in the same browser replaced the
  first account's records, and the first account lost its settings, day decisions and accepted check-ins; its days
  could be read again, those could not). Each account's records live under its own five keys, e.g.
  `cmaTdeeSettings:1234567` (`CMA.tdeeData.keyFor(base, userId)`); the value keeps its `userId`, checked on every
  read. Nothing of one account is ever written to, removed from or read into another account's keys.
* `cmaTdeeDays:<userId>` = `{userId, days: {'YYYY-MM-DD': {i, w, b, bp: [bmr, activity, exercise, tef], c, lf, s, cs?,
  f}}}` — i = row[0] kcal, w = first weigh-in kg, b = burned at fetch time, c = complete, lf = loggedFood, s =
  'rpc'|'csv', cs = the fields a CSV supplied ('i', 'w' or 'iw'), f = fetchedAt; about 80–120 bytes per day, so about
  30–45 KB per account-year and near 200 KB for 5 years of one account (quota 10 MB; 5 MB on Chrome 111–113); every
  further account that enables the tab adds its own.
* `cmaTdeeSync:<userId>` = `{userId, enabled, enabledAt, firstDay, lastFullAt, lastDeltaAt, energyChunk, flagsSource,
  prefs, rowLayoutVersion, lastError, notes, energyUnavailable}`; `cmaTdeeOverrides:<userId>` = `{userId, days: {iso:
  true|false}}` (kept apart from fetched data, so a refetch never clobbers a decision); `cmaTdeeSettings:<userId>` =
  `{userId, …settings}`; `cmaTdeeCheckins:<userId>` = `{userId, checkins: [… ≤ 260]}`.
* **Migration of the legacy keys** (the un-suffixed `cmaTdeeDays` … `cmaTdeeCheckins` of 0.3.0, only ever read and
  removed, never written), per key, when an account loads: a legacy value whose `userId` is that account's is copied
  (as stored) into its keyed slot when the slot is EMPTY - a keyed value is never overwritten - and the legacy key is
  removed only after that write succeeded (or when the slot already held this account's record: an earlier copy whose
  removal did not happen). The slots are read again right before the copy (another tab of the account may have
  migrated or saved meanwhile; two tabs migrating at once write the same copy, which Chrome reports once). A failed
  copy keeps the legacy value, the data is shown from it and the next load tries again; `disable({forget})` removes
  this account's legacy records too. A legacy value of ANOTHER account is left untouched (and not shown) until that
  account loads. Idempotent; writes bounded like every other.
* `otherAccountsStored` (status, diagnostics): the number of OTHER accounts with at least one TDEE key here (keyed
  keys from `chrome.storage.local.getKeys()` at load - a whole `get(null)` before Chrome 130 - plus the legacy
  records' userIds, then kept current from `onChanged`); a count only, never an id. A failed read is reported and
  nothing is written over what could not be read; writes are bounded (5 s). The nonce is never stored; `lastError` and log texts carry kinds, method names, dates and counts,
  never a reply value, a weight or an intake.
* The TDEE spec's `tdee.fetchLog` (its /export quota) does not exist: the GWT reads are not /export calls, so the
  "10 exports per day" limit does not apply. The /export CSV route is NOT implemented; the manual CSV import
  (Cronometer's own *Daily Nutrition* and *Biometrics* exports, YYYY-MM-DD dates only) is always offered. Daily
  Nutrition goes through the engine's `parseDailyNutritionCsv`; a date that repeats is refused (the *Food & Recipe
  Entries* export, servings.csv, has a Day and an Energy column per serving and would store each day's last serving),
  as is a file without a Date or an Energy column. Biometrics is read with the engine's `parseCsv`, NOT its
  `parseBiometricsCsv` (which converts only `lb*` units, so a stone amount became that many kg, and orders a day's
  rows by the text of the time, so '10:15 AM' came before '7:02 AM'): each Amount is converted by its own Unit (kg,
  lb / lbs, st / stone × 6.35029318; any other unit is skipped and counted in `unknownUnits`), and each day keeps its
  EARLIEST weigh-in by the parsed 12- or 24-hour Time (untimed after timed, then file order), the rule of the RPC
  weigh-ins; a file without Metric / Amount columns is refused.
